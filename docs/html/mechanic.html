Mechanic guide

Schema internals and the build

Everything needed to maintain the WARP schema and compile a database: what each file is, how the scripts work line by line where it matters, what the checks enforce, and where the sharp edges are. Assumes you've read the advanced guide for the concepts.

Compiling a full database

The Makefile builds the worked examples. A real database is the same pipeline over many StatementSet files: set STATEMENTS and ASSESSMENTS. Three constraints shape how you organize it:

1. Derivation is per file. The derivation scripts each take one input and one output. Statements only share a proposition object if they're in the same StatementSet. Two files with matching statements produce the same hash id (the key is deterministic) but separate proposition objects with separate derived_from_statements. To aggregate across sources, merge statement sets before deriving, or derive per file and union propositions by id afterwards.
2. References resolve only across the files you check together. check_refs.py and check_statements.py build their id index from the files on their command line. An assessment citing statements and propositions must be checked alongside the derived files that define them.
3. Cite stable ids. Derived ids are hashes of an identity key, stable across runs. A new version of a rule moves a group's ids only if it changes that group's key; open-question ids never change. Ids that annotators cite (a causal proposition in justified_by, a project in a criteria statement) are found by running derivation once and copying the id, as the examples do.

A sequence that respects all three:

# 0. One-time per template change
make patterns

# 1. Merge statement sets that should aggregate, then derive
python scripts/derive_strategies.py build/merged.yaml build/merged.derived.yaml
python scripts/derive_propositions.py build/merged.derived.yaml build/merged.derived.yaml
python scripts/derive_projects.py build/merged.derived.yaml build/merged.derived.yaml

# 2. Nodes, strategies and sites: expand_nodes takes any number of StatementSets
python scripts/expand_nodes.py templates/node_templates.yaml build/merged.derived.yaml \
  --owl project/nodes.ttl --sites project/sites.ttl --tsv-dir patterns/data

# 3. Shape validation and references: every file, including assessments
linkml-validate -s src/warp/schema/warp.yaml -C StatementSet build/merged.derived.yaml assessments/*.yaml
python scripts/check_refs.py build/merged.derived.yaml assessments/*.yaml

# 4. Semantic checks: everything that cross-references, in one call
python scripts/check_statements.py build/merged.derived.yaml assessments/*.yaml
python scripts/check_values.py build/merged.derived.yaml assessments/*.yaml

# 5. RDF, the projection gate, and the OWL lint
python scripts/export_rdf.py build/merged.derived.yaml assessments/*.yaml --out project/statements.ttl
python scripts/project_owl.py build/merged.derived.yaml assessments/*.yaml --out project/axioms.ttl \
  --report project/reports/projection.md --projects project/projects.ttl
make owl-check

The merge step isn't implemented in the repository. A merge must concatenate every list slot of StatementSet, dedupe by id, and fail if one id maps to two different objects (the same rule check_statements.py applies within a file). Open questions must be carried through untouched so their ids survive.

Schema architecture

Import, don't fork

imports:
  - linkml:types
  - upstream/sepio_classes      # SEPIO Core IM, pinned
  - upstream/causalmosaic       # CAMO 0.8.x, pinned
default_prefix: warp            # https://w3id.org/ecoweaver/warp/
default_range: string

Upstream files are vendored unchanged. All EcoWeaver changes are made in warp.yaml by:

  • is_a: subclassing SEPIO classes (EcoStatement is_a Statement, …);
  • slot_usage: narrowing inherited slots (range, required, identifier, inlining);
  • attributes: adding class-local fields;
  • own class_uris in the warp: namespace, so profile classes aren't mistaken for SEPIO's.

Vendoring rather than URL imports is deliberate: LinkML URL imports aren't pinned, and an upstream change must never silently change what data means.

Specialize, then leave the generic field empty

Following SEPIO's advice for profiles, generic Coding fields are specialized as named, enum-typed attributes, and the generic field must stay empty (enforced by check_statements.py):

What each enum becomes in OWL

Every profile enum says what its values are with implements:: owl:ObjectProperty for predicate enums, owl:NamedIndividual for the rest. CAMO's enums can't be annotated from the profile, so gen-owl runs with --default-permissible-value-type owl:NamedIndividual and clean_owl.py retypes CAMO's predicate values as object properties. SEPIO slots WARP uses get warp: IRIs through slot_uri in slot_usage, since SEPIO's own namespace is a placeholder.

Inlining and references

Which objects are nested and which are referenced by id determines what linkml-validate can and can't check.

Inlined (nested objects)Referenced by id
Every StatementSet list; hasEvidenceLines; contributions; recordMetadata; care; predicate_qualifiers; comparator; context; temporal_extent; source_spans; fillers; dataItems; sourceDataSet subject/object (→ nodes); proposition; targetProposition; derived_from_statements; contributor; knowledge_holders; reportedIn; evidence_item_refs (plain uriorcurie)

linkml-validate doesn't verify that references resolve, and evidence_item_refs isn't range-typed at all (an item can be a statement, study result, document or dataset record). Referential integrity is the job of check_refs.py, which walks every slot whose range is a class and isn't inlined (schema-driven, so a new group is covered as soon as its slots exist), and of check_statements.py, which checks the references it names.

The type field on objects names the concrete class (CausalStatement, EcoEvidenceLine, …) and is how the validator picks the class for polymorphic ranges.

Predicate-group registry

Scripts discover groups from annotations, so adding one needs no code changes. A group is any class carrying warp_group:

CausalStatement:
  is_a: EcoStatement
  annotations:
    warp_group: causal                          # part of the identity key
    warp_statements_slot: causal_statements     # StatementSet list of statements
    warp_propositions_slot: causal_propositions # StatementSet list of propositions
    warp_proposition_class: CausalProposition   # written as `type` on derived propositions

Three optional annotations:

AnnotationMeaning
warp_identity_extrasSpace-separated slot paths, in order, added to the identity key. Dotted paths reach into inlined objects: predicate_qualifiers.guidance.
warp_identity_ruleA rule name recorded instead of the shared one (criteria: warp-criteria-identity/1).
warp_derived_byThe script that derives the group, if not derive_propositions.py (implementation: derive_projects.py).

load_groups(schema_path) in derive_propositions.py:

  1. Builds a SchemaView and iterates all_classes().
  2. Skips classes without their own warp_group annotation (annotations aren't inherited here, so a subclass of CausalStatement isn't a group unless annotated).
  3. Resolves induced_slot("predicate", cls).range. If it isn't an enum, exits: <cls>: predicate range X is not an enum.
  4. Collects each permissible value's rosetta_template annotation for rendering.
  5. Returns groups sorted by group name. check_statements.py imports this same function.

The registry doesn't verify that the named slots exist on StatementSet; a typo just means the group finds no statements. Check the derivation report lists your group with the counts you expect.

Derivation algorithm

make derive runs three scripts per set, each IN OUT, then one across sets:

  1. derive_strategies.py (warp-strategy-identity/1): flattens one level of nesting, keys each strategy on the sorted (step, action) pairs of its required parts, mints node:strategy-<hash>, records it as the definition's canonical_node, and rewrites references to local strategy ids. A canonical id that moves is kept in replaces.
  2. derive_propositions.py (warp-prop-identity/4): propositions for every registered group not derived by another script. Below.
  3. derive_projects.py (warp-impl-identity/1): clusters implementation statements by shared external id, or same subject, same site and overlapping periods (union-find), and writes one project record per cluster.
  4. transfer_costs.py: explicit cost transfers under a versioned rule in config/cost_transfer/, to examples/cost_statements.transferred.yaml.

Identity key and id

identity_key = "|".join([group, subject, predicate, object,
                         "negated" if negated else "affirmed", scope])
identity_key += "".join("|" + path + "=" + canonical_json(value)   # each warp_identity_extras path, in order
                        for path in extras)
proposition_id = "warp:prop/" + sha1(identity_key).hexdigest()[:12]

Extras are canonical JSON (sorted object keys; lists sorted unless list_elements_ordered). A missing extra is null: the statement still groups with others missing it, and the report counts it. The rule version is recorded on the proposition and is not hashed, so a group with no extras (causal, interaction) has the six-field key alone.

Subject and object are compared as raw node id strings: no normalization, no reasoning. Two different node ids for the same OWL class are different propositions. Keep node ids canonical.

Per group

  1. Seed with open questions. For each existing proposition in the group's list: if status == open_question, set raised_as_question: true. Keep only propositions with raised_as_question; reset their key, rule version, derived_from_statements: [] and status: open_question. Every other existing proposition is discarded: derived propositions are rebuilt from scratch.
  2. Walk statements. If scope is missing, empty or unclear: remove proposition, remove targetProposition from its evidence lines, record it as skipped, continue.
  3. Compute the key. Look it up; if absent, create a proposition with the hash id, type = the group's proposition class, s/p/o, negated, scope, the extras' values, rendered propositionText.
  4. If the match is a raised question with no description yet: move its question text to description ("Raised as an open question: …") and replace propositionText with the rendered fact.
  5. Set status: asserted, key, rule version; append the statement id to derived_from_statements (no duplicates).
  6. Set the statement's proposition, and targetProposition on each of its own evidence lines.
  7. Write propositions sorted by id; drop the list if empty.

Rendering

text = rosetta_template.format(subject=node.name, object=node.name, **extras)
       # fallback: "{subject} <predicate with _ → space> {object}"
if negated: text = "it is not the case that " + text
prefix = {assertional: "In a particular case, ", contingent: "Sometimes, ",
          prototypical: "Typically, ", universal: "Always, "}[scope]
text = prefix + lowercase_first_char(text)  + "."

Node names are inserted verbatim, so a capitalized node name mid-sentence stays capitalized ("…prevents Population growth rate of…"). Names come from the set's own nodes, then from the sets given with --names; a value that is not a CURIE (an enum value such as degraded_area) reads with spaces for underscores.

Output and guarantees

  • Writes # GENERATED by scripts/derive_strategies.py, derive_propositions.py and derive_projects.py (warp-prop-identity/4). Do not edit derived records by hand. then yaml.safe_dump. Comments in the input are not preserved.
  • Report to stdout: per group, each proposition id, status, text and source statements. Skipped statements to stderr. Exit status is 0 even when statements are skipped.
  • Idempotent: running on its own output gives the same result. tests/test_derived_ids.py fails if any committed derived file differs from a fresh derivation.

Statement checks

check_statements.py FILE [FILE …] [--schema PATH]. Covers what SEPIO leaves to "additional tooling". Exit status 1 on any error.

How it indexes

walk_ids collects every object with a string id, at any depth, in every file: statements, propositions, agents, contributions, evidence lines, documents, study results, data items, datasets. All become resolvable reference targets. Within one file, an id seen twice must map to identical objects (so a dataset inlined under two study results is fine if the copies match). Across files, ids are unioned without comparison.

Warnings

  • A statement or assessment with no author contribution.
  • An annotated statement with no annotator in recordMetadata.contributions.

Assessments are checked with annotated=False: they may fill direction/strength, and don't need an annotator. A statement class whose schema requires direction (criteria verdicts) may fill it too. Agents are looked up for the CARE rule only if they appear in some file's top-level agents list. Agent kinds of authors not in any file are treated as unknown (no CARE requirement), though the unresolved contributor reference is itself an error.

Grammar:

ClassExpression := (genus CURIE | var NAME)  AND  Restriction*
Restriction     := property CURIE  some  ClassExpression

That's EL: intersections and existential restrictions. Unions, negation, subClassOf-only patterns, data properties and list variables aren't supported; adding them means changing templates_lib.py and gen_dosdp.py together.

Composite (management_strategy) and particular (site) templates have no vars or equivalent_to and get no DOSDP pattern; they are filled in strategy_definitions and site_definitions. expand_nodes.py writes canonical strategies as rdfs:subClassOf planned process and has part some each required action, and, with --sites, each site as an owl:NamedIndividual without geometry. A node with a refinement is written as a subclass of its template's expression and left out of the fill tables.

check_template (templates_lib.py)

Run by both generators. Raises TemplateError for: duplicate var names; a level with both or neither of genus/var; a genus, property or var range without a label in terms; a term used as the wrong kind; vars used but undeclared; vars declared but unused; {placeholders} in name/definition that aren't vars. Unknown prefixes fail in expand_curie.

DOSDP keyFrom

Also writes patterns/prefixes.yaml (sorted). Errors per template are printed and the script exits 1 after processing the rest.

expand_nodes.py: node definitions → OWL + TSV

For each node_definitions entry, in every StatementSet given:

  1. Template must exist. Every declared var filled exactly once; no undeclared vars; filler CURIE prefix in allowed_prefixes; if the node has an entity_type, it must equal the template's camo_entity_type. Problems are collected, not fatal, until the end.
  2. Label and definition: name/definition filled with filler labels (falling back to CURIEs), whitespace collapsed.
  3. OWL: owl:Class with rdfs:label, IAO:0000115 definition, dcterms:conformsTo the pattern IRI, and owl:equivalentClass built recursively (intersection of head and owl:someValuesFrom restrictions). Every referenced class and property is declared, so the file is a standalone OWL 2 EL ontology.
  4. TSV row: defined_class, defined_class_label, then <var>, <var>_label per var. Rows are deduplicated by node across files and sorted.

It doesn't check that a filler is actually a subclass of the var's range: that needs the ontologies, and is left to ODK/ROBOT. Exits 1 listing every problem, so it's CI-safe.

Two routes, same axioms

Turtle from expand_nodes.py, or dosdp-tools generate on the patterns and fill tables (make owl-dosdp, or an ODK repo: copy patterns to src/patterns/dosdp-patterns/, TSVs to src/patterns/data/default/, set use_dosdps: TRUE). The logical axioms were confirmed identical with robot diff.

  • project/warp.owl.ttl: the profile as OWL 2 DL, from gen-owl then clean_owl.py, which reports each change it makes (eight jobs, each a candidate upstream LinkML issue; see docs/rdf-owl.md §9.1). RDF, OWL and reports

The contract is docs/rdf-owl.md. In short:

  • Two layers. The logical layer (node classes, strategy classes, site and project individuals, projected axioms) is OWL 2 EL. The reification layer (export_rdf.py) is every record as named individuals, with inlined records at <owner>/<slot> IRIs, no blank nodes, enum values as IRIs, and ISO dates verbatim plus xsd:dateTime bounds.
  • Statements point at nodes through annotation properties (warp:subject, warp:predicate, warp:object), and each non-negated statement also gets one relation triple. Group polarity hooks are in export_rdf.py's RELATIONS: recommendations, costs and criteria verdicts pick a sub-property, never the abstract parent.
  • The projection gate (project_owl.py): universal scope, not negated, every statement observed, a supporting synthesis assessment. Group projections are in its PROJECTIONS dict; no entry means the group projects nothing. Causal, interaction and tolerance's has_habitat project existential subsumption with a warp:derived_from annotation. On the examples nothing passes, by design.
  • One IRI, one kind. If a new slot name already exists with a different kind of value (literal vs IRI), give it its own slot_uri, or check_owl.py will report the IRI as two kinds. Sentinel values are listed once, in SENTINELS in clean_owl.py.

Profiles

A profile is WARP restricted to some predicate groups, declared in config/profiles.yaml (groups, optional lists, example sets) and generated by subset_schema.py into project/profiles/warp_<name>.yaml plus a relations file without the other groups' predicates. The closure keeps the shared core and anything a kept element refers to (ranges, including inside any_of and rules; is_a; mixins; class slots; slot_usage keys). Imports are rewritten to the vendored upstreams; no IRI changes, so a profile is a strict subset of warp.yaml. build_profile.py runs the core pipeline with --schema and fails if a set's derived records differ from the full build's. Group-specific checks and reports are not part of a profile build.

Reports are findings, not validation errors: projection.md, guidance.md/.csv, tolerance.md, cost_completeness.md/.csv and target2.md, all in project/reports/.

Extending WARP

Add a node template

Full guide: docs/node-templates.md. In short:

  1. Design the shape as a phrase with blanks, leaving out direction of change. Reuse an existing template if the logical shape matches.
  2. Add every fixed class and property to terms with its current OLS label (labels drift: RO:0000052 is now characteristic of); add new prefixes.
  3. Add the template entry. Keep allowed_prefixes tight. Use an id containing an underscore (see gotchas).
  4. make patterns, then fill it in a node_definitions entry and make nodes.

Released templates are frozen. Changing one's logical definition silently changes every node made with it. Make a new id and mark the old one deprecated.

Add a predicate group

Full guide: docs/predicate-groups.md. All edits in warp.yaml:

  • Predicate enum, each value with a meaning (checked in OLS) and a rosetta_template annotation
  • Qualifier class, avoiding SEPIO slot names (direction, strength, score, subject, predicate, object, qualifier)
  • Statement class: is_a: EcoStatement, own class_uri, the four warp_* annotations (plus warp_identity_extras if anything beyond the six shared fields decides identity), subject/predicate/object constrained and required, negated with ifabsent: "false"
  • Proposition class: is_a: EcoProposition, same constraints, carrying the identity extras
  • Two StatementSet lists, named exactly as in the annotations, inlined_as_list
  • Node templates for the subjects and objects
  • RDF and OWL: predicates WARP mints declared in warp-relations.ttl; polarity in export_rdf.py's RELATIONS; projection, or an explicit "none", in project_owl.py; the five questions in docs/rdf-owl.md §8 answered and the register updated
  • An example set added to STATEMENTS; tests; make all passes; the derivation report lists the group; README and changelog updated

Change the identity rule

  1. Edit identity_key() (and the module docstring) in derive_propositions.py.
  2. Bump RULE_VERSION. Every proposition records it.
  3. Re-derive everything. Ids change only for groups whose key string changed; open-question ids never change. Re-point anything that cites a moved id, and update tests/test_derived_ids.py.
  4. Record the change, and which ids moved, in CHANGELOG.md; update the README's derived-records table.

Gotchas

  • Derivation drops comments from the input YAML. Keep annotator commentary in fields (description, original_text), not YAML comments, if it must survive.
  • Derivation drops hand-written asserted propositions silently.
  • Derivation is per file; see compiling a full database.
  • Node identity is string identity during derivation. Two node ids with equivalent OWL definitions still split propositions.
  • make clean deletes all of project/, including committed outputs, and all of patterns/*.yaml.
  • check_statements.py reads the derived files (a superset of the inputs) and the assessments; linkml-validate, check_refs.py and check_values.py read the inputs too.
  • Duplicate-id comparison is per file only. The same id used for different objects in two files isn't detected.
  • The scripts/ directory must be importable: several scripts import templates_lib, warp_schema or derive_propositions. Running them by path (python scripts/x.py) handles this.
  • Mid-sentence capitals in rendered proposition text come straight from node names.
  • Derived ids annotators cite are pasted by hand. A causal proposition in justified_by or a project in a criteria statement is found by running derivation once; if its key changes, the citation needs re-pointing.
